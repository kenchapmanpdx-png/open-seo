## WO-B27-001 — a site that refuses the app's crawler name is still read

- Red case: evolvedmechanical.com, no audit; start check "did not answer". Red test at `verifyWebsite` (public entry): `fork/runs/b27/wo001-002-red.txt`.
- Cause confirmed, and it differs from the WO. Probe, read only, one request each (ADR-039 table): the full app name `Mozilla/5.0 (compatible; OpenSEO-Handbook/1.0; …)` and a Chrome browser string are both dropped; `OpenSEO-Audit/1.0`, `curl/8.5.0` and `OpenSEO-Handbook/1.0 (+https://openseo.so)` get 301 → 200. The site's firewall drops clients that claim "Mozilla" without a browser's handshake. Reading as a browser (the WO's fix) would not have read this site.
- Class fix (one derivation point, `engine/safe-fetch.ts`): `shortNameRetry`. A default-name request that is dropped (non-timeout network error) or answered 403 / 406 is sent once more with the short name `OpenSEO-Handbook/1.0 (+https://openseo.so)`; answered → the fetcher keeps the short name for the rest of the unit; refused too → the first outcome stands and no further retest. On for the start check and the run's site fetcher. Same robots token, same pacing.
- Report: `coverage.shortName` from the crawl → run page info line "This site refuses the app's full crawler name; pages were read with the short name OpenSEO-Handbook/1.0."; exports append "read with the short app name" to the depth line. No severity, no score effect.
- Guards: SafeFetch tests (switch after one refusal; both names refused → no switch, no further retest; a site answering the full name and requests naming their own user-agent are never retested); `verifyWebsite` tests; `capNotes` test.
- Live: `verifyWebsite("evolvedmechanical.com")` → ok (was "did not answer"); antiquecandleco.com → ok.

## WO-B27-005 — small sites do not lose AI-judged items to the budget split

- Red: `createRunBudget` test with the wellnessforzebras.com numbers (34 pages, $0.84, map $0.11): judge got $0.336 (`fork/runs/b27/wo005-red.txt`).
- Cause confirmed: `llm/budget.ts` gave the judge a fixed 40 % whatever the map stage spent; the map share sat unspent.
- Fix: `RunBudget.setMapSpent`; judge budget = total − map spend (capped at the map share). The app sets map spend = profiles this run created (`HandbookPageProfileRepository.runCostUsd`, project + run scoped) + this unit's mapper spend. Map spend + judge spend ≤ total, so total spend never exceeds today's auto budget. CLI (`handbook-audit.ts`) does not set it and keeps 60 / 40.
- The BLOCKED reason already names the spend and budget (`llm budget: $X spent of $Y`); Y is now the judge's real limit.

## WO-B27-003 — scope is decided before the run, inside the app

- Red case: the scope for antiquecandleco.com came from `field-test.ts --preflight` and a chat rule; the app showed only "Whole site (up to 500 pages)".
- Cause confirmed: no preflight in the app. The two limits already resolve to one number in `runScope` (min of the Handbook cap and the audit's `maxPages`); the run page quoted them as two notes.
- Fix: `services/scopePreflight.ts` (`sitemapCensus` runs the run's own robots and sitemap collectors; `decideScope` applies step 3); server function `previewHandbookScope`. Check a site, Whole site, no sections typed: the page shows "The sitemap lists N pages; the page limit is L. Automatic core scope: leave out … so K pages are in scope", prefills the sections, and "Start check" runs with the list as edited. `checkSite` without a scope (any unattended caller) takes the automatic one; Quick samples and leaves nothing out. The decision is stored on the run (`coverage.scope`) and printed at the top of the report; the run page quotes one limit (scope notes replace the two limit notes).
- No sitemap: "No sitemap; scope was decided while crawling (page limit L)."
- Guards: `decideScope` (34 pages whole; exactly the limit whole; archives first then the largest section to 90 %); `checkSite` takes the automatic scope when none was chosen.
