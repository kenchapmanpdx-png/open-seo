### WO-B12-003 — Sidecar stall recovery (image 1.2.1)

Sidecar (`fork/sidecar/server.ts`):

- Each render / axe / Lighthouse task runs in its limiter slot with a hard deadline: render = request `timeoutMs` + 60 s (default 90 s), axe 120 s, Lighthouse 240 s. Past it → HTTP 504 `{ "error": "deadline" }`. The slot stays held until the engine settles (honest concurrency).
- Stall: 2 misses within 10 min, or a task still running at 2× its deadline (checked every 15 s) → one log line, `exit(1)` once pending responses are written (5 s grace). Docker restarts the container (`restart: unless-stopped`).
- Browser recycle after `HANDBOOK_SIDECAR_RECYCLE_AFTER` tasks (default 500) when no task is in flight; new tasks wait for the relaunch.
- `/health` and K3 shapes unchanged. `SIDECAR_VERSION` and compose image 1.2.1.

Engine (`collectors/sidecar-collectors.ts`, `sidecar-per-url.ts`):

- Client timeout = deadline + 30 s: render 120 s, axe 150 s, Lighthouse 270 s (were 90 / 90 / 180 s, shorter than the new sidecar deadlines). Timeout or 504 → page outcome `sidecar timeout` (skipped, run continues).
- Per-run gate: 3 timeouts in a row → calls wait 60 s, `/health` probed once; healthy → resume, else every later call fails `sidecar unavailable` without reaching the sidecar. The probe is spent after one use: a second streak of 3 timeouts marks the sidecar unavailable (conservative default: no endless 60 s waits).

Tests: sidecar never-resolving render → 504 at the deadline, second miss → injected exit called once; engine gate → resume on healthy probe, `sidecar unavailable` on a failed one.
