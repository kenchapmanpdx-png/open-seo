### Cause (step 1 diagnosis, `fork/runs/b24/wo001-diag.txt`)

- Apex `aweandorderorganizing.com` 301s to `www.`; `www` is Weebly / Square Online behind Cloudflare (`server: cloudflare`, `x-host: grn165.sf2p.intern.weebly.net`).
- Plain fetch of `https://www.aweandorderorganizing.com/` returns **200** with the page for each of three UA strings: a non-browser UA, the headless Chrome UA (`HeadlessChrome/131`) and the standard Chrome UA. The crawl collector also read 7 pages with 200 (in-app audit `1566ec0c…`, `share403or429 = 0`).
- The sidecar render (Playwright Chromium, default context, no UA override in `fork/sidecar/render.ts`) gets **403** on both the JS and no-JS render. Lighthouse (its own Chrome launch) is not refused.
- SUPPORTED: the UA string alone is not the trigger (the headless UA string over plain HTTP gets 200). SPECULATIVE: Cloudflare bot management keys on browser-level automation signals of the Playwright context (headless fingerprint / `navigator.webdriver` / TLS + UA combination). Not narrowed further: a direct authenticated sidecar `/render` call from the shell was refused by this session's permission guard, so the diagnosis rests on the stored run reason, the live in-app rerun (still 403) and the plain fetches.
- Step 5 (standard UA for render) **skipped**: the trigger is not the UA string alone, and no handbook section or ADR permits changing the render UA (ADR-013 lists the sidecar render UA as one of the fork's own identities). Anything beyond that would be evasion (batch rule). For Ken: no change made; "keep the helper UA" is the state.
