# WO-B22-001: effect map: every check names its search or AI effect

- Batch: B22 · Class: HEAVY · Size: M
- Contracts: additive optional finding field `effect` (report schema, `contracts/exports.ts`, like `categories` in ADR-029); no `CONTRACTS_VERSION` bump; no schema or migration change
- Depends: —
- Registry items: all 129 (`registry.json`) + 26 SUPP (`registry-supp.ts`)

## Problem (SUPPORTED)

- Ken's rule (2026-11-18): include a check only if it affects Google rankings, SEO or GEO. `registry-tags.json` records only the audience (SEO / GEO / AEO; 14 items have none); nothing records **why** an item matters, and the fix list (`client/features/handbook/fixList.ts` `FIX_GROUPS`) puts S3 + S4 together as "nice".
- Handbook text and scoring are Ken's verbatim sources: this WO classifies and folds, it does not remove checks or change grades.

## Spec

1. New fork-owned file `src/server/features/handbook/registry-effect.json`: `{ "<id>": { "effect": "search" | "ai" | "both" | "hygiene", "reason": "<one line>" } }` for every REGISTRY and SUPP id.
   - `search`: affects crawl, indexing or ranking signals the handbook states. `ai`: affects retrieval or citation by AI answers (GEO / AEO) as the handbook states. `both`. `hygiene`: no search or AI effect stated in the handbook (accessibility, brand, owner records, tidy-ups).
   - The basis is the item's own handbook text and `refs`; no outside ranking claims, no traffic or backlink data. `reason` quotes the item's claim in ≤ 15 words or reads "no search or AI effect stated in handbook §<ref>".
   - A classification not obvious from the text defaults to `hygiene` with that reason (conservative: it folds, never deletes). List every such item in the report for Ken.
2. Report: `effect` per finding = strongest of its items (`both` > `search` / `ai` > `hygiene`), derived beside `withCategories` (`engine/categories.ts`), single place. SUPP-only findings follow the same rule.
3. Fix list: inside the "nice" group, findings whose effect is `hygiene` fold into one collapsed "Housekeeping (no direct search or AI effect)" section, count shown, collapsed by default. S1 / S2 findings are never folded whatever their effect (a hygiene item at S1 / S2 is listed in the report as a classification question). CSV export gets an `effect` column. Grade card, counts behind the grade, exports' finding lists unchanged.
4. Decision default: the grade still counts hygiene items (formula verbatim). "For Ken: say 'hygiene out of grade' to remove them from scoring" (a scoring change, its own batch).

## Guards

- `registry-effect.test.ts` (pattern of `registry-tags.test.ts`): key set equals REGISTRY + SUPP ids; every entry has a valid effect and a non-empty reason; `effect !== "hygiene"` requires non-empty registry `refs` (SUPP: non-empty `refs`); a new check without an entry fails `pnpm test`.
- `fixList.test.ts` at `buildFixGroups`: hygiene-only S3 / S4 → housekeeping; mixed hygiene + search finding stays visible; S2 hygiene stays visible; totals equal the unfolded total.
- Report contract test: `effect` optional, old stored reports parse.

- Cross-check against Semrush verdicts: a finding both tools reported (`agree` in any `fork/reports/field-*.md`) classified `hygiene` is listed for review (a signal the classification or Semrush row is wrong); no silent override either way.

## Do not

- Delete or rename a check, change severities or `S1_CAP`, edit `registry.json` (handbook-sync must stay 0 diffs), claim a ranking effect the handbook does not state.
