Googlebot / Bingbot results on this run: not in my notes: step 1 reads them from the run's stored `botFetch` evidence (project `9f7aa0c2-1421-43aa-a820-1102994463bc`, latest run) and records the per-bot table.

## Class

Severity of a bot-access finding ignores which crawler is blocked. A block that leaves Google and Bing untouched cannot stop indexing (ADR-034 principle "S1 only where an indexable page is affected") yet caps the grade at 39, and a new bot can enter the fetch list unclassified.

## Decision (default)

- Search crawlers `Googlebot`, `Bingbot` failing (not intermittent) → S1 as today. Only AI crawlers (`GPTBot`, `OAI-SearchBot`, `ClaudeBot`, `PerplexityBot`) failing → **S2**, no cap, `severityReason` "AI-crawler-only block: Googlebot and Bingbot receive the page; a deliberate block is allowed (record it under P9-04)". Mixed → S1 listing both groups. Intermittent stays S2.
- One report per evidence: `ai-bot-policy.ts` omits tokens already named in the P9-01 parity finding; if none is left it emits no S4 finding. P9-04 stays BLOCKED with the per-token decisions to record.
- "For Ken: say 'AI-bot block always S1' to revert." ADR-034 addendum (ADR-037).

## Steps

2. **Class constants** in `contracts/collectors.ts` beside `BOT_USER_AGENTS`: `SEARCH_BOTS` and `AI_BOTS`, both `as const`; type check that their union equals `keyof typeof BOT_USER_AGENTS` (a new bot without a class fails `pnpm types:check`).

4. `ai-bot-policy.ts`: skip tokens present in the parity finding (same run result, via the check context's findings or the shared failing-bot set; implementer picks the simplest existing mechanism, no new contract).
5. `engine/s1-scope.ts` (ADR-034 table): P9-01 stays an access item; add a test line that P9-01 can be S1 only when a search bot failed.
6. BadGEO: `_bots.json` page with `["ClaudeBot"]` only → `P9-01:S2`; page with `["Googlebot"]` → `P9-01:S1`. Check the existing `/partners/acme.html` (`GPTBot`) expectation: it moves to S2 with a note in `_expect.json` history / report, not silently.
