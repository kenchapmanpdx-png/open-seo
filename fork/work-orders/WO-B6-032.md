## Spec

- Run = tracker prompts × configured providers (`byok_ai_tracker_provider`), concurrency 2 per provider, budget `BYOK_RUN_BUDGET_USD` (default 2) checked before each call; over → answer `failed` with error `budget`.
- Per answer: raw output JSON to the evidence store (`raw_output_path`); sources with category/page type (WO-B6-030); matches via the upstream matcher (reuse, no copy); `ai_web_query` rows in provider order, `normalized` = lower/trim, `is_fanout` = normalized non-empty and ≠ normalized prompt.
- Schedule job: `byok_ai_schedule.next_run_at <= now` → start run, advance `next_run_at` by `interval_days` before running (no double start).
- Never touches upstream billing/credits.

## Conventions

- Tables already exist (B5 R4a): import them from `@/db/integrations-tables` (provider-aware); never from a dialect file. Repository → service → server fn (AGENTS.md). Every query is scoped by `organization_id` (project rows) or joins to a scoped parent. Server fns live in the feature folder (`functions.ts`, pattern: `src/server/features/handbook/functions.ts`); repository tests use a real SQLite test DB (pattern: `src/server/features/ai-visibility/aiVisibilityTestDb.ts`).
- Jobs are registered in `src/server/features/handbook/scheduled/forkScheduledJobs.ts` (`*/5 * * * *` or `17 3 * * *` list). Each job is idempotent and bounded (batch size in the spec).
