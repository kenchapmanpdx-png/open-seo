# WO-B27-004: the limit is spent on the right pages, and a hit limit is reported exactly

- Batch: B27 · Class: HEAVY
- Source: Project chat instructions 2026-11-28 (B26 WO-091 run 108: evolvedmechanical.com no audit; antiquecandleco.com audit `5cdbb86c` capped; wellnessforzebras.com llm budget); owner order 2026-11-28 "no failed starts, no silent caps; find each cause and fix it".

- Red case: audit `5cdbb86c`: 481 in-scope sitemap URLs, crawl stopped at 500, 452 read.
- First: from the stored crawl list of `5cdbb86c`, count in-scope sitemap URLs not read, and the non-sitemap URLs that took slots, grouped by pattern (query parameters, pagination, other). Put the table in the report.
- Fix:
  1. Order: in-scope sitemap URLs are fetched first, round-robin across sections so every section gets pages before any section is exhausted. Discovered non-sitemap URLs come after.
  2. A discovered URL that differs from an already-queued or read URL only by query parameters is a variant: recorded with its source page (P3-04 and link checks keep their evidence), fetched at most once per parameter pattern as a sample, and not counted against the page limit. A parameter URL that is listed in the sitemap or is self-canonical is a real page and counts.
  3. Limit reached → the run completes. The report top states: the limit, pages read, in-scope sitemap URLs not read (count, and the list grouped by section), discovered URLs not followed (count). Sitewide findings state "based on N of M in-scope pages".
  4. No run may end with unread in-scope sitemap URLs while non-sitemap URLs were read, unless the report says so with the counts.
- Guards: a site under the limit behaves as today (same pages read on the eight goldens; list any change). Parameter URLs that are the only URL of a page (no clean twin) are still read.
- Do not: raise the limit to hide the problem.
